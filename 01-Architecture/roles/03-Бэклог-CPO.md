## 2. Идеальные Продуктовые Таблицы Выбора (Map-Reduce Architecture)

При **ЛЮБОЙ** продуктовой или системной развилке банда обязана создать матрицу выбора строго формата **20x20** (20 объектов на 20 параметров = 400 ячеек). *(снято 2026-08-28: канон 5–6×8–12, см. шапку)*

### ⚙️ МУЛЬТИАГЕНТНАЯ ОРКЕСТРАЦИЯ ТАБЛИЦ (Domain Sharding)

Чтобы не сойти с ума при сборе 400 параметров, запрещено отдавать сбор одному агенту. Применяется архитектура **Map-Reduce**:

1. **Map (Domain-Based Sharding):** Запусти 4–5 субагентов. Разделяй нагрузку **ПО ПАРАМЕТРАМ, а не по объектам**. *(лимит Hermes: ≤3 одновременно, волнами)*
    - _Пример:_ Агент 1 ищет только "Батарею и Терморегуляцию" для всех 20 объектов. Агент 2 ищет только "Производительность CPU/GPU". Это делает агента узким специалистом и снижает галлюцинации.
2. **Формат отдачи (JSON-only):** Субагенты обязаны возвращать собранные данные **СТРОГО в формате JSON** (массив объектов), а не в Markdown. LLM часто ломают Markdown-таблицы при большом объеме.
3. **Кросс-Валидация (Spot-Check):** Готовый JSON передается 3-м агентам-Критикам. Критик выбирает случайные 10 ячеек из собранных данных и делает HTTP-запрос по ссылкам-пруфам. Если хоть одна ссылка `404` или цитата выдумана — вся порция JSON бракуется и воркер переделывает её.
4. **Reduce (Сборка и Математика):** Главный Агент берет верифицированные JSON-чанки, запускает Python-скрипт (`run_command`), который:
    - Склеивает чанки в единую матрицу.
    - Нормализует баллы по формуле Min-Max.
    - Считает ROI и генерирует финальные `.md` и `.json` файлы.

<critical_rules>

2. **Запрет на генерацию моков (No Stubbing):** Категорически запрещено использовать Python-скрипты для генерации "рыбы" таблиц (усредненных значений). Для каждой ячейки агент обязан сходить в интернет.

## 3. Архитектура Бэклога и Глубокая Декомпозиция

Продукт декомпозируется по иерархии: **Продукт -> Блок -> Подблок -> AI-Задача (Leaf Task)**.

### Иерархическая Приоритизация (Nested Priority)

Приоритизация гнездится (вкладывается). Искусственный интеллект должен всегда четко понимать:

1. Какой _Блок_ продукта имеет высший `block_priority` (например, Core Engine = 100, UI = 50).
2. Какой _Подблок_ внутри этого блока имеет высший `subblock_priority`.
3. Какая _Задача_ внутри подблока имеет высший ROI (`priority_score`).

### Строгие критерии AI-Задачи (Definition of Ready):

- **Объем:** Оценка ведется в **Agent-Minutes** (10–15 минут работы агента).
- **Acceptance Criteria (AC):** Жесткие критерии приемки.
- **Active Sprint Threshold:** Активное окно планирования (статус TODO) до 100–300 задач, остальное в ICEBOX. *(снято: активное окно 10–40 + ICEBOX)*

## 4. Хранилище Бэклога (Data Layer: SQLite WAL)

Бэклог хранится в SQLite по пути: `08-Backlog/backlog_{ИМЯ_ПРОЕКТА}_{VERSION}.db`.

### 4.1. Внутреннее Версионирование (Audit Trail & Migrations)
- Регулярные внешние бэкапы backlog-БД (ветка разработки): daily ×7 + weekly ×4, только через `sqlite3.backup()`, в 08-Backlog/backup/; в АНАЛИЗе — рекомендация-строка, не действие.

- **Аудит:** Таблица `tasks_history` с триггерами `AFTER UPDATE/INSERT/DELETE`.
- **Миграции (Схема БД):** Запрещается прямой `ALTER TABLE`. Используй `schema_migrations (version, applied_at)`. Любые изменения — через `.sql` файлы в `migrations/`.

### 4.2. Обязательная структура таблицы `tasks`:

- `task_id` (PK), `block`, `subblock`, `title`, `description`, `acceptance_criteria`.
- `depends_on_task_id`: Указание зависимости (для графа выполнения DAG).
- `block_priority`: Приоритет родительского блока (0-100).
- `subblock_priority`: Приоритет подблока (0-100).
- `agent_minutes`: Оценочное время работы ИИ-агента в минутах.
- `user_value`: Оценка ценности фичи (1-100).
- `priority_score`: = `user_value / agent_minutes` (ROI фичи).
- `status`: ICEBOX, TODO, IN_PROGRESS, REVIEW, DONE, BLOCKED.
- `assigned_agent_id`, `test_logs`.

### 5.1. Hub-and-Spoke Оркестрация
