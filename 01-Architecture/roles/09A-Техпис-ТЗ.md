Каждое ТЗ и каждый промт исполнителю ОТКРЫВАЕТСЯ блоком из 5 пунктов простыми словами — до любых технических деталей:
1. **Что чиним** — что именно чиним или делаем (1–2 строки, языком продукта, не кода).
2. **Цель** — чего хотим добиться.

Стороннее предупреждение допустимо только с доказательством (файл библиотеки, строка, ссылка на трекер) и только если не вызвано нашим неправильным использованием. В отчёт — дамп и таблица «сообщение | файл:строка | штук | исправлено/стороннее».
5. **Данные — независимый пересчёт выборки.** Цифры из отчёта (количества, суммы, хеши) пересчитать отдельным скриптом прямо по файлам/БД, не через код, который их создавал; 3–10 случайных записей вручную.
6. **Запрет подкрутки тестов:** нельзя подменять функции приложения в тесте, ослаблять пороги, увеличивать таймауты без причины, отключать/пропускать проверки, переписывать ожидаемое под фактическое. Любая правка теста — отдельной строкой отчёта с причиной. Надзор ищет это первым.
7. **Регрессия:** все ранее исправленные баги по проекту — в список повторной проверки (адрес/шаг + ожидаемое); каждый новый исправленный баг получает автотест или запись в этот список.
8. **Доказательства:** у каждой цифры приёмки — путь к файлу (json, снимок, лог). Без пути цифра не засчитывается.
9. **Окружение (environment-limited):** красный прогон из-за окружения (таймаут сервера, нехватка памяти, сеть) — один повтор; если снова красный — статус `environment-limited` с причиной и логом, не «PASS» и не бесконечные повторы.
10. **Независимая проверка:** после исполнителя — отдельный свежий агент (не исполнитель, не его продолжение), только чтение, по чек-листу: подкрутка тестов, пересчёт данных, свой живой проход п. 2–4, сверка каждой цифры отчёта с доказательством. Итог — файл REVIEW с таблицей «пункт | подтверждено/нет | цифра | доказательство». Циклы самопроверки исполнителем не заменяют этот шаг.
11. **Критика текста ТЗ** — не больше 2 проходов; дальше ТЗ уходит в работу, а сомнения — в раздел «открытые вопросы».

### Б. Общие правила для каждого ТЗ

1. **Сначала баги, потом функции.** Пока в проекте есть открытые баги работоспособности (не открывается, нет данных, красная консоль) — новые функции и пересчёты данных в ТЗ идут в раздел «отложено до нуля багов».
2. **Порядок внутри багов:** работоспособность → консоль → подсказки/пустые состояния/вёрстка → шрифты и мелочи.
3. **Имя файла ТЗ:** `TZ-{проект}-{суть-словами}-{YYYYMMDD}-{HHMM}-v{N}.md`. Суть — что делаем (2–5 слов). Запрещены в имени: «доделка», «доработка», «остаток», «хвосты». Новая версия = новый файл; старый — копия в архив + в шапке строка `ЗАМЕНЕНО ДД.ММ.ГГГГ ЧЧ:ММ → <новое имя>`.
4. **Одно действующее ТЗ на проект.** Блоки выполняются подряд в одном ТЗ; незавершённое из старого ТЗ переносится в новое явным списком, а не остаётся «где-то в старых».
5. **У каждого блока:** проблема → решение → результат → цифра приёмки → откат (что и куда скопировать до правки).
6. **Отчёт исполнителя:** первая строка — адрес тестовой страницы/стенда (если есть) обычным текстом; таблица «блок | статус | цифра | доказательство | время»; последняя строка — по канону закрывающей строки (`ПОЛНОСТЬЮ закончен ответ — ДД.ММ, ЧЧ:ММ (UTC+3)` или `Закончен промежуточный ответ — …`); незакрытое — выше неё.
7. **Промпт для исполнителя:** последняя строка промпта повторяет главное требование (например: «Повтор: только баги, приёмка — живой браузер + консоль 0/0 + независимая проверка»).
8. **Простой язык:** без жаргона без объяснения; термин — один раз расшифровать в скобках.
9. **Красные линии** (удаление, перезагрузка, чужие сервисы, принудительные команды git, публикация) — отдельным разделом в каждом ТЗ.
10. **Числа, а не слова:** «работает» = измеримый признак (например «объектов на экране >0», «ошибок 0»).
