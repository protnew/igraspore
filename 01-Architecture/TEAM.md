## 🔄 Поток работы (Workflow)

### Фаза 1: Анализ и проектирование

```
Задача → [01 Архитектор] → Таблица выбора → [02 Математик] → Проверка расчётов
                                                            ↓
                                              [09A Техпис] → ТЗ (TZ-*.md)
```

1. **Вход:** Новая фича или задача от владельца (Алексея)
2. **Роль 01 (Архитектор Развилок):** Создаёт таблицу выбора (5-6 вариантов × 8-12 критериев)
3. **Роль 02 (Таблицы):** Проверяет математику, считает ROI, нормализацию
4. **Роль 09A (Техпис):** Пишет ТЗ по канону `TZ-{PP}-{YYYYMMDD}-{NN}-v{V}.md`

### Фаза 2: Детализация

```
ТЗ → [03 CPO] → Бэклог → [04 UX] → Макеты → [05 DBA] → Схема данных
```

5. **Роль 03 (CPO):** Декомпозиция ТЗ в задачи бэклога (Product → Block → Subblock → Task)
6. **Роль 04 (UX):** Дизайн интерфейса, токены, состояния элементов
7. **Роль 05 (DBA):** Проектирование схемы данных, миграций

### Фаза 3: Инфраструктура и безопасность

```
Схема → [06 DevOps] → Инфра → [07 SecOps] → Аудит безопасности
```

8. **Роль 06 (DevOps):** Настройка CI/CD, контейнеров, деплоя
9. **Роль 07 (SecOps):** Аудит безопасности (OWASP, секреты, зависимости)

### Фаза 4: Реализация и контроль

```
Код → [08 Контролёр] → Аудит → [09 QA] → Тесты → Релиз
```

10. **Роль 08 (Контролёр):** 10-векторный аудит кода, проверка структуры
11. **Роль 09 (QA):** Zero-Point Scan, написание и прогон тестов
12. **Релиз:** После зелёного прогона всех тестов

## 🤝 Протокол передачи (Handoff)

### Активный handoff (передача между ролями)

Каждая роль может передать находку другой роли через JSON-структуру:

```json
{
  "handoff": {
    "from_role": "04-UX",
    "to_role": "05-DBA",
    "domain": "Данные профиля игрока",
    "trigger": "Обнаружена потребность в хранении пользовательских настроек",
    "context": "UX-архитектор спроектировал экран настроек, нужны поля: язык, громкость, управление",
    "severity_hint": "MAJOR",
    "findings": ["F04-1", "F04-2"]
  }
}
```

### Правила handoff

1. **Без context — игнорировать:** Пустой контекст = передача невалидна
2. **severity_hint — из enum:** `BLOCKER | CRITICAL | MAJOR | MINOR | TRIVIAL`
3. **Принимающая роль** разбирает в `accepted_handoffs` своего JSON-отчёта
4. **Орфография:** ПЕРЕПИНЫВАНИЕ (исправлять ошибки ввода)

## 🚦 Светофор статусов

### Статусы выполнения (шкала качества)

| Статус | Значение | Действие |
|--------|----------|----------|
| 🟢 **Сделано/Определено** | Полностью выполнено, есть пруфы | Принять |
| 🟡 **Есть вопросы** | Частично выполнено, нужны уточнения | Вопрос владельцу |
| 🔴 **Не сделано** | Не выполнено или выполнено неверно | Доработать |

### Серьёзность находок (шкала проблем)

| Severity | Значение | Срок фикса |
|----------|----------|------------|
| 🔴 **BLOCKER** | Блокирует работу, релиз невозможен | Немедленно |
| 🟠 **CRITICAL** | Критично, но есть workaround | До релиза |
| 🟡 **MAJOR** | Существенно, влияет на качество | В этот спринт |
| 🟢 **MINOR** | Незначительно, косметика | В бэклог |
| ⚪ **ICEBOX** | Идея на будущее | Когда-нибудь |

## ⚠️ Красные линии (запреты)

### Общие запреты для всех ролей

1. **Нет физическому удалению:** Никогда не использовать `DELETE`, `DROP`, `TRUNCATE`, `os.remove`, `shutil.rmtree`. Только soft-delete (`in_trash=1`).
2. **Бэкап перед записью в БД:** `sqlite3.backup()` перед любой операцией записи.
3. **Нет сетевым настройкам ПК:** Не изменять hosts, DNS, прокси, firewall, маршруты. Только диагностика.
4. **Нет записи в продукт без ТЗ:** Код менять только по `TZ-*.md` с блоком 5 вопросов.
5. **Лимит 500 строк:** Файл >500 строк = CRITICAL. Разделить.
6. **Коммит после каждого шага:** Незакоммиченная работа недопустима.

### Специфичные запреты по ролям

- **Роли 01-04 (Аналитика):** НЕ писать код, НЕ менять БД, НЕ коммитить в продукт
- **Роль 05 (DBA):** НЕ использовать `DROP`/`DELETE`, только миграции и soft-delete
- **Роль 06 (DevOps):** НЕ хардкодить секреты, НЕ использовать `eval`/`exec`
- **Роль 07 (SecOps):** НЕ эксплуатировать уязвимости на проде, только диагностика
- **Роль 08 (Контролёр):** НЕ писать код, только аудит и отчёты
- **Роль 09 (QA):** НЕ мокровать функции в тестах, НЕ ослаблять пороги без причины
- **Роль 09A (Техпис):** НЕ писать код, только документы

## 📊 Дисциплина сдачи (Zero-Point)

### Обязательные артефакты сдачи

1. **ТЗ файлом:** `TZ-*.md` с блоком 5 вопросов (путь + число строк)
2. **Все тесты физически прогнаны:** Лог + команда повторения + итог «N passed/M failed/K skipped»
3. **≥10 скриншотов:** Уникальные кадры с подписью и стендом (≥3 моб + ≥3 десктоп + ≥3 изменённых)
4. **Анализ ≥3 ролями:** Разработчик + пользователь + ещё одна роль; находки с якорями
5. **Таблица «пункт → доказательство»:** С цифрами и путями к файлам

### Формат отчёта исполнителя

```markdown
## ОТЧЁТ ИСПОЛНИТЕЛЯ

**Адрес тестовой страницы:** http://127.0.0.1:8890/

| Блок | Статус | Цифра | Доказательство | Время |
|------|--------|-------|----------------|-------|
| B1   | 🟢     | 5/5   | [путь к логу]  | 10:30 |
| B2   | 🟡     | 3/5   | [путь к скриншоту] | 10:45 |
```

## 📝 Использование команды

### Как запустить роль

1. Открыть файл роли в Qoder (например, `01-Архитектор-Развилок.md`)
2. Скопировать содержимое в промпт агенту
3. Добавить задачу: «Отработай ТЗ [суть] (N строк): [путь к TZ-*.md]»
4. Агент выполнит роль и создаст отчёт в `09-Docs/out-dev-factory/`

### Пример промпта для агента

```
Ты — Роль 01 (Архитектор Развилок) проекта iGraSpore_V2.
Прочитай файл роли: 01-Architecture/roles/01-Архитектор-Развилок.md
Задача: Выбрать технологию для рендеринга игрового мира.
Контекст: Нужен 2D/3D гибрид, целевые платформы PC + мобильные.
Ограничения: Open-source, лицензия MIT/Apache, производительность 60 FPS.
Выход: Таблица выбора в 09-Docs/out-dev-factory/01-forks.md
```

### Оркестрация через Teams

Qoder Teams позволяет делегировать задачи субагентам:

1. **Leader agent** получает общую задачу
2. **Делегирует** субагентам с ролями (01-09A)
3. **Субагенты** выполняют и возвращают отчёты
4. **Leader** агрегирует результаты и принимает решение
