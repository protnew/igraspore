🧮 ТОЧНАЯ МАТЕМАТИКА (Min-Max Normalization)
Используй эти формулы в своём Python-скрипте:

Прямая логика (Больше = Лучше): Оценка = ((Значение - Min) / (Max - Min)) * 10
Обратная логика (Меньше = Лучше): Оценка = ((Max - Значение) / (Max - Min)) * 10 (Min и Max — худшее и лучшее значение среди исследуемых объектов).
Полезность (Итоговый балл): Взвешенная сумма SUM(Оценка * Вес).
Полезность/Стоимость (ROI): (Полезность / Цена) * 1000.
*(решение владельца 21.10.2026 №2=2.1: Winner = max Σ(Оценка×Вес); ROI — справочная колонка, финальную таблицу НЕ сортирует; margin — в шкале Σ; множитель 1000 — только масштаб отображения)*

## 3. Архитектура Бэклога и Глубокая Декомпозиция

Продукт декомпозируется строго по 4-уровневой иерархии: Продукт -> Блок -> Подблок -> AI-Задача (Leaf Task).

### Строгие критерии AI-Задачи (Definition of Ready - DoR):

- **Объем:** 10–15 минут работы субагента (1 прогон).
- **Емкость (LOC):** 300-500 строк кода максимум.
- **Acceptance Criteria (AC):** Ни одна задача не попадает к кодерам, если в ней не прописаны жесткие критерии приемки (как QA будет ее проверять).

### Критерии Достаточности:

- **Minimum Viable Backlog:** От 100 позиций (для MVP небольшого проекта). *(снято: масштаб списка = 10–40 + ICEBOX)*
- **Maximum Threshold:** Ограничение активного окна планирования до 100 000 задач, если больше разбиваем на несколько запрсоов.

## 4. Хранилище Бэклога (Data Layer: SQLite WAL)

Бэклог проекта должен всегда храниться в локальной базе данных SQLite (режим WAL). Имя базы данных должно строго соответствовать названию проекта и лежать по пути: `08-Backlog/backlog_{ИМЯ_ПРОЕКТА}.db` (пробелы заменять на подчеркивания). ИИ-агенты не должны использовать Markdown-файлы как основной источник правды для задач, все чтение и запись статусов идет только в эту БД.

### 4.1. Внутреннее Версионирование (Audit Trail)

- Создается таблица `tasks_history`.
- Вешаются `AFTER UPDATE`, `AFTER INSERT`, `AFTER DELETE` триггеры на таблицу `tasks` для отслеживания всех изменений (кто, когда, что изменил).

### 4.2. Внешнее резервирование (Backups)

Регулярные дампы БД: Раз в день, Раз в неделю, Раз в месяц, Раз в год (`backlog_daily.sqlite` и т.д.).

### 4.3. Обязательная структура таблицы `tasks`:

- `task_id` (PK), `block`, `subblock`, `title`, `description`, `acceptance_criteria`.
- `depends_on_task_id`: Указание зависимости (для графа выполнения DAG).
- `loc_capacity`: Оценочное кол-во строк кода. *(справочно; канон — 03: user_value/agent_minutes)*
- `user_value`: Оценка ценности фичи (1-100) + тег MoSCoW (Must, Should, Could, Won't).
- `priority_score`: = `user_value / loc_capacity` (ROI фичи). *(справочно; канон — 03: user_value/agent_minutes)*
- `status`: TODO, IN_PROGRESS, REVIEW, DONE, BLOCKED.
- `assigned_agent_id`, `test_logs` (для логов QA).

## 5. Мультиагентная Оркестрация: 10 Ролей (Swarm Mode)

### Рой Управления и Проектирования (Аналитика)

**1. CPO (Визионер):** Проводит бенчмаркинг лидеров рынка. Разгоняет масштаб продукта. Внедряет фреймворк `MoSCoW` для жесткой фильтрации. Архивирует задачи с меткой `Won't`. **2. Business Analyst (Декомпозитор):** Разбивает блоки на задачи. Отвечает за `Definition of Ready` и прописывает железобетонные `Acceptance Criteria`. Задача без AC считается недействительной. **3. Value Appraiser (Оценщик Ценности):** Кросс-чекает ценность с фичами конкурентов. Проставляет `user_value` (1-100). Адвокат пользователя. **4. System Architect / Estimator:** Оценивает задачи в `loc_capacity`. Создает параметрические таблицы выбора. Строит граф зависимостей (DAG), заполняя поле `depends_on_task_id`, чтобы кодеры не ломали продукт параллельной работой. **5. DBA / Data Engineer:** Поддерживает здоровье SQLite. Внедряет алгоритм **Exponential Backoff**: если агент получает ошибку `SQLITE_BUSY`, он обязан подождать и повторить транзакцию, а не падать. *(справочно; канон — 03: user_value/agent_minutes)*

### Рой Исполнения и Контроля (Workers)

**6. Frontend UX/UI (Дашбордист):** Генерирует HTML-дашборд. Отслеживает "Бутылочные горлышки" (например, 50 задач скопилось в REVIEW) и подсвечивает их красным алером для оркестратора. **7. Lead Worker (Старший Кодер):** Делает SQL-запрос `WHERE status = 'TODO' AND depends_on_task_id IS NULL ORDER BY priority_score DESC LIMIT 1`. Выполняет архитектурные задачи. Обязан сгенерировать файл `context-handoff` после создания фундамента, чтобы рядовые кодеры знали паттерны. **8. Parallel Swarm Worker (Рядовые Кодеры):** Массовая параллельная разработка. **Правило изоляции:** Каждая задача выполняется в отдельной Git-ветке (`git checkout -b task/MSG-VID-001`), чтобы 5 агентов не перезаписывали один и тот же файл одновременно. **9. QA Engineer (Тестировщик):** Слушает статус `REVIEW`. Гоняет тесты 4-х уровней (Anti-Hallucination Protocol). **Обязан** записать физический лог терминала (stdout/stderr) в поле `test_logs` в БД. Врать о прохождении тестов физически невозможно. **10. Security Auditor / SecOps:** Финальный гейт. Помимо ревью кода, сканирует новые зависимости (NPM/Python). Если добавлена новая либа — блокирует задачу до создания таблицы выбора. Переводит в `DONE` и делает Git Merge.

## 6. Алгоритм Автоматизации (No-Touch Cycle)

1. CPO сканирует конкурентов, формирует векторы. Аналитики и Архитекторы создают DAG-граф задач с ROI, LOC и AC в SQLite.
2. Субагенты-кодеры запрашивают свободные независимые задачи (`depends_on` выполнено), создают изолированную Git-ветку и пишут код (до 300 строк).
3. При конфликтах БД (Lock) используется Exponential Backoff. При готовности базы (архитектуры) Lead Worker скидывает `context-handoff`.
4. QA-агент гоняет физические тесты и прикрепляет stdout лог прямо в SQLite.
5. SecOps проверяет зависимости, сливает Git-ветку в main и закрывает задачу.
6. Дашбордист отрисовывает актуальное состояние. Пользователь только наблюдает. *(в ветке АНАЛИЗ канон — 3 круга критики: HARDEN 2026-09-18; «5 итераций» оригинала не исполнять)* *(лимит Hermes: ≤3 одновременно, волнами; invoke_subagent — не инструмент Hermes)* *(канон имени бэклог-базы — в 03: с `_{VERSION}`)* **Источник правды канона:** `01-АНАЛИЗ\00-ВЫВОД-ДЛЯ-АЛЕКСЕЯ.md` + `CHOSER_UI_PROJECT_TAG_CANON.md`; текст ниже — зеркало.
